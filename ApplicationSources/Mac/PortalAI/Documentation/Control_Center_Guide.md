# PortalAI Control Center — 2026-10-16

Help now has six categories: Getting started; Chat, history and vision; Images, video and audio; Science and automation; Diagnostics and maintenance; Home Assistant and recovery. All topics and each category are alphabetically ordered, with Quick start pinned first. Search filters title, aliases, category and content. Context links clear incompatible filters and select the matching topic.

The six primary Controls buttons and existing theme/layout are preserved. Right-click menus recognize current maintenance names, open the same confirmation sheets as the buttons, and recheck account/exit guards when dispatched.

Open PortalAI.exe in the portable root. Settings lists installed Qwen profiles, backend choices, context limits and multimedia preferences. Controls → Startup saves pending chat settings, adopts a matching healthy model or switches an idle owned model. Finish active work first; Stop cancels work when needed. Media and vision specialists load on demand instead of being started together.

Accounts is between Welcome and Controls. Its Current Account card shows the signed-in username and role. The yellow Change current user button opens another sign-in without ending the current session. Cancel and incorrect credentials keep that session open. Accepted credentials stop current work, save and seal the current profile, then open the selected account with fresh chat and account state. Export Data offers Chat history, Outputs or Both in one verified ZIP. The red administrator-only Start fresh action follows Change current user and requires an additional final confirmation after its existing review and authentication steps.

Packages shows the installed chat models, Standard/Abliterated 2B and 4B vision companions, backend files, native FLUX/SD1.5, CPU music/speech, multimedia/science and mission/VM components. Presence means files were detected, not that a model is running or the recipient hardware was validated. Models shows loaded state and mission arming. Saved model policy is in Settings. Persistence sits after Settings; Maintenance follows it before Help and holds diagnostics and storage tools.

The image/video inventory includes both checkpoints (including SD 1.5 for CPU/NVIDIA fallback) and diffusion weights, with relative paths and sizes. LoRAs appear separately, including nested adapter folders. Adapter presence does not establish base-model compatibility or Radeon support. Navigation uses content-sized buttons so Settings fits in the default single row.

Persistent missions have their own Persistence main tab, also linked by the launcher and tray menus. Full is current-user host access; Observe is a capability restriction; VM isolates guest shell actions only. Model/controller remain on the host. Stop cancels chat and pauses missions before terminating owned components. Exit stops and closes; minimizing leaves work running. Interrupted actions require review.

In Persistence, select the Schedules subtab to create a one-off or repeating mission. Enter a local first-run time or leave it blank for now, an interval in minutes (0 = once), an action budget per run, and a run limit (0 = until stopped). Creation is paused; Enable starts supervision. Missed occurrences coalesce into one run, and runs never overlap. Stop/Exit pauses all schedules across restart. Resume/review a blocked active mission before re-enabling its schedule. A completed schedule needs a new schedule to authorize more runs.

The agent can remember(key,text) and recall(query). Memory survives restart and is shared within a mission family or recurring schedule, with source-mission provenance and access-mode checks. It is separate from chat memory and contains agent notes, not independently verified facts. Previous checkpoints are retained for review, never replayed automatically. The SSD must remain connected and the host awake with PortalAI running. Scheduling requires supported supervision on the current host; Linux supervision additionally requires delegated cgroup v2.

GUI reports retain timestamps, actual outcomes and Current + Previous. Run buttons request a fresh result. One maintenance check runs at a time. See Diagnostics.md and Maintenance.md for coverage. The newest code takes effect on the next GUI launch.

Login uses a rounded account banner, muted gray descriptions and a turquoise Sign in button. The shutdown page uses muted gray descriptions and progress text. The red Retry verified shutdown button is right-aligned and becomes available if stopping or account verification fails; PortalAI closes only after verified sealing succeeds.

Web search uses the existing Brave API route when BRAVE_SEARCH_API_KEY is supplied, then DuckDuckGo HTML and Lite. Successful results have a five-minute SSD cache with an explicit age. HTTP refusals/rate limits have bounded cooldowns instead of repeated requests; blocked page fetches are distinguished from search failures. Maintenance → Targeted Diagnostics → Web Tools → Run selected makes a live search request. No account/key was created and no new web dependency was installed.

Gold-bordered Save and Cancel stay visible across tabs; effort changes apply after Save. History is the first toolbar action, immediately left of Edit last. The chat toolbar, transcript, history and composer each have their own border; collapsed traces use one quiet outline. Expanded traces retain an ornate outer frame and a slim header outline.

## Native workflow display — 2026-10-17

The Windows host adapter now exposes the Persistence page's real “Missions & access” and “Schedules” navigation buttons once each. The launcher no longer registers a second set of aliases for those same buttons. The Home Assistant dashboard/card and its installer were not changed; the duplicate controls came from the PortalAI host's native workflow description.

Native form serialization now resolves Tkinter's internal PY_VAR handles against the live Tk interpreter before publishing control labels, values, and select-option labels. If a handle no longer resolves, the UI shows an empty value rather than the implementation token. This keeps the native workflow readable without changing the underlying local Tk controls or account permissions.
