# Windows r62: profile photo retrieval repair

Nice could find an identity but miss its photo because the structured page reader discarded image links. Its cached text also lost the HTML needed for image discovery and tables. Extensionless photo URLs were saved as .data.

The reader now returns ranked image candidates, keeps a bounded HTML cache for discovery, and preserves image/source evidence when chat context shrinks. Profile images, related people and default avatars have explicit hints. The web workflow checks an identified profile before broadening search. Person-photo downloads reject likely placeholders and use the validated image extension. Structured web image searches share the existing progress and time limits.

Validation: Each installed SSD previously ran **878 application checks: 877 passed and one unavailable symlink fixture skipped**. Each SSD also passed 91 targeted checks after the final cache/evidence corrections. Another 70 web/runtime checks and all six live public-web smoke checks passed. The final extracted Windows packages each ran 878 checks: **875 passed, one skipped, and two OAuth loopback tests hit a host transport problem**. These two errors also reproduce on the unchanged installed OAuth code: a raw socket diagnostic shows the server's Content-Length header replaced in transit with Transfer-Encoding: chunked without body framing. A TLS fixture attempt failed recipient certificate verification. The complete packaged suite is therefore not reported as passing; the unchanged OAuth files and every extracted payload hash were verified, and all changed image/web tests passed. No HTTP parser or TLS verification was weakened. Installer checks, seven embedded runtime/source resources, catalog routing and the Academic compiled download-launcher preparation were verified. Real public retrieval on both SSDs followed a linked Scholar profile, saved its portrait, and rejected a GitHub identicon before publication in **1.36/1.14 seconds**. This tested the actual HTTP/tool path, not a new Qwen 27B model-generated conversation. No production account was used.

Added payload: **26,182 bytes** relative to r61. No new dependencies, models or background services. Extra HTML storage is bounded to two million characters per worker, at most one million per page. Optional avatar geometry uses existing portable Pillow and at most a one-megapixel input sampled at 32x32. Unknown analysis stays unknown; there is no face recognition or guarantee of pictured identity.

D/E remain independent Full installations with more than 80 GiB free. Windows and Universal Windows routes are r62; Linux/Mac remain r51. Other physical hardware and full fresh-recipient installation were not tested. Restart PortalAI normally to load the update.
