Immediate live incident: the Aoostar GUI and projection worker kept the same
processes. A read-only rich_index returned native_chat_modal. Chat instructions
was open behind Welcome. Closing that dialog with its X (without saving) made
rich_index and chat describe succeed. The owner confirmed HA recovered.
Account, modal, rich-read, attachment and request-replay guards remain intact.
No host runtime patch or additional host restart is required for this repair.

Separate reproducible HA frontend bug: accept() renders attachment status while
refresh.fetching is still set. refresh finally clears fetching without drawing
buttons/status again. With an open host modal, upload fields are absent, so the
old Loading attachment controls text remains after the request has finished.
The initial-read error path also has no settled attachment status.

Fix: refresh redraws buttons/status only when it still owns the current fetch;
attachmentNotice calls a genuinely in-flight request Loading, and gives a
Refresh controls instruction when no usable model has been obtained. Current
same-account, same-form, viewer epoch, modal, no-replay and upload checks remain.
This does not close host dialogs automatically or send pending messages.

initial request failure settles to Refresh controls guidance; a late reply
cannot redraw after disconnect. The first two fail on portable-1; all 83 JS
